# 架构蓝图：从零复刻一套「六部」

这套架构的本质是**把 Agent 的能力与上下文从运行时里剥出来，变成你自己拥有、
可版本控制、可跨设备同步的资产**。

很多人的现状是：技能装在 Agent 里，上下文散在对话中，换个设备或换个 Agent 就
要从头再来。这套架构把两者分别收拢到两个 git 仓库，让它们脱离具体运行时独立存在。

---

## 一文一武：两个仓库

```
~/skill-repo/      能力层（六部）  —— 用什么干活
~/life-os/           上下文层（识海） —— 在干什么
```

两者是**平级**的，都被 Agent 通过 `external_dirs` / bootstrap 引用，位置固定不动。
`~` 根目录只放这两个系统级仓库，其他一切项目进 `~/work/<项目名>/`。

---

## 组件 1：唯一真源（skills/ 目录）

**做什么**：所有自己写的技能集中在一处，别处只放软链。

```
~/skill-repo/
└── skills/
    ├── my-writer/         # 真源
    ├── my-charts/         # 真源
    └── _office/           # 共享基础设施（多个技能共用）
```

**为什么**：复制的副本必然分叉。改了一处忘另一处，是「不知道哪个是最新的」的根源。
软链让 Agent 的加载路径不变，但内容只有一份。

**接入方式**（各 Agent 不同）：

```yaml
# Hermes
skills:
  external_dirs:
    - /home/you/skill-repo/skills
```

---

## 组件 2：索引技能（最高优先级）

**做什么**：一个 SKILL.md，要求 Agent 在做任何事前先读它，再决定用哪个技能。

```markdown
---
name: skill-repo-index
description: "Load this skill BEFORE any other skill ... 本仓库是唯一真源，
             优先级高于任何 Agent 自带技能。"
category: productivity
---

# 技能索引（最高优先级）

## 规则：先查这里，再决定用哪个技能
1. 先 ls ~/skill-repo/skills/，找到能力匹配的那个
2. skill-repo 与 Agent 自带技能冲突时，skill-repo 赢
3. 按能力匹配，不按名字匹配

## 同名陷阱表
| 任务 | 正确选择 | 自带错误选择 | 差异 |
```

**为什么**：同名不同物是常态（`pptx` vs `powerpoint` 工具链完全不同）。
不建立优先级，Agent 会随机选一个，选错代价是整轮会话白跑。

**三行规则足矣**：先查真源 → 冲突时真源赢 → 按能力不按名字。

---

## 组件 3：配套上下文层（life-os / 识海）

**做什么**：另一个 git 仓库，装「在干什么」——项目进度、日程、身份信息、内容产出。

```
~/life-os/
├── WORKING.md        # 当前占用登记：哪台设备在改哪个技能/项目（含 TTL）
├── PROJECTS/         # 项目进度
├── PROFILE.md        # 个人信息
└── CONTENT/          # 内容产出（薄索引，深度内容回各自仓库）
```

**配套一个 bootstrap 技能**：新设备/新 Agent 上岗时加载，clone 两个仓库并输出接续汇报。

**为什么**：能力层回答「用什么干活」，但没有「在干什么」的上下文，Agent 每轮都是
从零开始。两层分开是因为**更新频率和隐私级别不同**——技能很少动，上下文天天变；
技能可以开源，上下文含隐私红线（证件/卡号/token 永不入 git）。

**铁律**：深度内容回深仓库。学习笔记去学习仓库，产品文档去产品仓库的 PRODUCT.md。
上下文层只装**薄索引**，否则会变成第二个垃圾堆。

---

## 组件 4：跨设备同步机制

**做什么**：让两个仓库在多台设备间保持一致。

```
hooks/
├── post-commit              # commit 后自动 push + 通知
└── skill-repo-sync-check.sh   # 只 fetch 检测远程更新，输出确定性
```

**同步检测**（每小时）必须按运行时能力二选一：

| 运行时 | 方案 |
|---|---|
| 有 Hermes | cron + monitor 模式：无变化时 agent 不运行，**零 token 成本** |
| 其他（StepCode 等） | 内置 cron + prompt 里写决策分支：无输出/失败 → 静默结束 |

**为什么 monitor 模式是关键**：普通定时任务每小时必跑一次 agent，哪怕什么都没变。
monitor 模式由脚本输出决定是否唤醒 agent，没变化就是零成本。

**`external_dirs` 的软链也要同步**：换设备时脚本要重建软链，否则 Agent 加载不到。

---

## 组件 5：占用登记（防多设备冲突）

**做什么**：改任何共享资源前先查有没有别的设备正在改。

`~/life-os/WORKING.md`（两仓库共用一个登记处）：

```
- 设备: wsl-laptop
  资源: skill-repo/pptx
  开始: 2026-09-25 14:00
  TTL: 2h
```

**规则**：改技能前先 `git pull` 再读 WORKING.md；出现他人登记且 TTL 未过 → 停下问用户。
开工登记一行，完工撤销。

**为什么**：多设备同时改同一个技能，后 push 的那个必然冲突或覆盖。2 小时 TTL 是
折中——足够覆盖一次工作会话，又不会因为忘了撤销而永久锁死。

---

## 组件 6：治理规则（AGENTS.md）

**做什么**：写给 Agent 的通用规范，与具体技能无关。

至少包含：

- **诚实性（最高优先级）**：做不到就说做不到，绝不用看起来合理的假输出冒充真实执行结果
- **只改真源**：不要拷贝到别处再改
- **仓库只存规则与脚本，不存素材**：图片/视频等大二进制一律进 `~/work/<项目名>/`
- **判断标准**：换个项目还能复用 → 进仓库；只服务某个项目 → 进 workspace
- **每台设备有专属 git 身份**，提交信息格式固定
- **冲突时 `pull --rebase` 重推，绝不 `push --force`**

**为什么**：这些是「每次都会遇到、但每次都要重新解释」的事。写一次，所有 Agent 都遵守。

---

## 组件 7：装机流程（install.sh）

**做什么**：新设备一条命令接入。

```
1. clone 两个仓库到固定位置（~/skill-repo、~/life-os）
2. 配置 git 身份（设备专属，如 wsl-laptop）
3. 装 hooks（post-commit、sync-check）
4. 配 external_dirs 指向真源
5. 装每小时同步检测
6. 跑自检清单，打印结果
```

**为什么**：架构的价值取决于最低配的那台设备。没有一键装机，实际结果是
「三台设备里两台没同步，一致性即失效」。

---

## 落地顺序

不要一次建完。按依赖序：

1. **真源 + 软链**（组件 1）—— 先让内容只有一份
2. **索引技能**（组件 2）—— 让 Agent 认这份真源
3. **AGENTS.md**（组件 6）—— 立基本规矩
4. **装机 + 同步**（组件 4、7）—— 才能上第二台设备
5. **上下文层 + 占用登记**（组件 3、5）—— 多设备协作时才需要

前 3 步单机就能获益；第 4 步之后才能叫作「跨设备架构」；第 5 步是多设备并发编辑的
安全网，设备少于两台可以先不建。

---

## 最小可用版本

如果只想快速验证价值，**只需要组件 1 + 2**：一个 git 仓库装技能 + 一个索引进
`external_dirs`。半小时能建完，立刻解决「技能散落各处、改哪份不知道」的问题。

其余组件是在这个基础上逐层加的，不是前置条件。
